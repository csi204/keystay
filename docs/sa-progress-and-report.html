ตำแหน่งงานและบทบาทที่ได้รับมอบหมาย (Role & Responsibilities)

0.50 คะแนน

ในโครงงาน KEYSTAY ผมได้รับมอบหมายให้ทำหน้าที่ในตำแหน่ง System Analyst (SA Lead) ควบคู่กับ Full-Stack Developer โดยมีบทบาทหลักคือการเป็น "สะพานเชื่อมระหว่างบริบททางธุรกิจของโรงแรมขนาดเล็ก (5–10 ห้อง) เข้ากับสถาปัตยกรรมคลาวด์สมัยใหม่ (Cloudflare Edge Architecture)"

Pain Point โรงแรมขนาดเล็กที่ผมนำมาวิเคราะห์

  • ซอฟต์แวร์โรงแรมใหญ่ (Opera/Cloudbeds): แพงเกินไป คิดค่าธรรมเนียมรายเดือนสูง และระบบเทอะทะซับซ้อนเกินกว่าโรงแรม 5-10 ห้องจะใช้งานได้คล่องตัว
  • การจดสมุดหรือใช้ Excel: ก่อให้เกิดการจองห้องชนกัน (Overbooking) โดยเฉพาะจังหวะแขก Walk-in เข้ามาพร้อมแขกออนไลน์
  • การเก็บเงินตกหล่น: พนักงานลืมบันทึกบิลค่าน้ำมินิบาร์ ค่าซักรีด ก่อนแขกเช็คเอาต์ ทำให้โรงแรมสูญเสียรายได้

ขอบเขตความรับผิดชอบจริงของผม

  • Domain Modeling: ออกแบบวงจรชีวิตห้องพัก (Room State Machine) 7 สถานะอย่างรัดกุม
  • Backend Services: พัฒนา 40 APIs บน Cloudflare Workers (Reservation 24 APIs + Billing 16 APIs)
  • Database Architecture: ออกแบบฐานข้อมูล Cloudflare D1 (SQLite) พร้อมทำ Atomic Batch Transactions
  • Frontend Portal: พัฒนาหน้าจอ Front Desk & Cashiering Portal บน React 19 รองรับทั้ง PC และ Tablet

🔹 2.1 การออกแบบ Room Lifecycle State Machine (7 สถานะรัดกุม)

หัวใจหลักของซอฟต์แวร์โรงแรมคือความถูกต้องของสถานะห้องพัก ผมได้กำหนดกฎทางธุรกิจและสร้าง Guard ในระดับ API ให้สถานะห้องพัก 7 สถานะเปลี่ยนข้ามกันได้เฉพาะเส้นทางที่ถูกต้องตามตรรกะเท่านั้น:

Available ──(จองล่วงหน้า)──► Reserved ──(Check-in)──► Occupied ──(Check-out)──► Checked Out ──► Cleaning ──► Available │ │ ▲ └────────(Walk-in 1-Click)──┴─────────────────────────┘ *กฎเหล็ก SA: ห้อง Occupied ห้ามเปลี่ยนเป็น Available โดยไม่ผ่าน Check-out | ห้อง Maintenance ห้ามถูกเปิดขายในปฏิทิน

🔹 2.2 การพัฒนาระบบ Backend Services & Database (40 APIs)

Reservation Microservice (24 APIs)

พัฒนาบน Cloudflare Worker บริการรับผิดชอบเรื่องแขกและการจองห้องพัก:

  • POST /api/v1/walk-in: รับแขกหน้าร้าน สร้าง Guest + Booking + Check-in จบในคลิกเดียว
  • POST /api/v1/reservations/:id/check-in: เช็คอินแขกที่จองล่วงหน้า บันทึกเวลาและเงินมัดจำ
  • POST /api/v1/reservations/:id/check-out: เช็คเอาต์ ปรับสถานะห้อง และส่ง Event Fan-out 1:4
  • GET /api/v1/reservations/calendar: ค้นหาห้องว่างโดยตรวจจับ Date Collision
Billing & Cashiering Microservice (16 APIs)

พัฒนาบน Cloudflare Worker บริการรับผิดชอบเรื่องบิล การเงิน และใบเสร็จ:

  • POST /api/v1/bills/:id/items: เพิ่มรายการมินิบาร์ ค่าอาหาร หรือค่าเสียหายเข้าสู่ Folio
  • POST /api/v1/bills/:id/pay: ชำระเงิน ปิดบิล หักลบเงินมัดจำกุญแจอัตโนมัติ
  • GET /api/v1/bills/:id/receipt: ออกใบเสร็จรับเงิน/ใบกำกับภาษีทางการพร้อมแจกแจง VAT 7%
  • GET /api/v1/bills/by-room/:roomId: ค้นหาบิลที่ยังไม่ปิดตามหมายเลขห้องพัก

🔹 2.3 การสร้าง Data Integrity ด้วย Cloudflare D1 Batch Atomic Units

ในจังหวะเช็คอิน หากคำสั่ง SQL รันแยกกัน อาจเกิดปัญหาเน็ตหลุดกลางคันทำให้ห้องถูกปรับเป็น Occupied แต่ประวัติการเข้าพักไม่ถูกบันทึก ผมจึงออกแบบให้ใช้ await db.batch([...]) รัน 3 คำสั่ง SQL พร้อมกันเป็น Atomic Unit เที่ยวเดียว หากคำสั่งใดล้มเหลว ระบบจะ Rollback คืนค่าทั้งหมดทันที 100%

🤝 2. การทำงานร่วมกับ "บุญ" (QA Lead)
  • Asynchronous Event Fan-out 1:4 (จังหวะ Check-out): เมื่อแขกเช็คเอาต์ที่เคาน์เตอร์ของผม ระบบจะยิง Event เข้า Upstash QStash และกระจายงานไปยัง Housekeeping Service ของบุญโดยอัตโนมัติ เพื่อสร้างงานทำความสะอาดด่วนทันที
  • Quick Emergency Contacts Integration: นำ Outsource Contacts API ที่บุญดูแล มาเชื่อมต่อกับ Emergency Drawer หน้าร้าน ให้พนักงานต้อนรับโทรเรียกช่างซ่อมฉุกเฉินได้ใน 1 คลิก

  2. ชี้ให้ดู จุดสีสถานะบนพื้นกระจก Tempered Glass และการจัดกลุ่มแยกชั้น 1-2
  3. คลิกปุ่ม "เปิดห้อง / Walk-in" บนการ์ดห้องว่าง (เช่น ห้อง 101)
  4. โชว์ Center Split Modal ที่เปิดขึ้นตรงกลางหน้าจอ
  5. กรอกชื่อแขกทดสอบ คุณสมชาย ใจดี, เบอร์โทร และกดยืนยัน
  6. การ์ดห้อง 101 จะเปลี่ยนเป็นสีน้ำเงินเข้มสถานะ Occupied ทันที
🗣️ สคริปต์คำพูดคุณเดียร์:

"นี่คือหน้าจอทำงานหลักของพนักงานต้อนรับครับ ผังห้องพักถูกออกแบบเป็น 4 คอลัมน์ แยกชั้นชัดเจน และใช้ Auto-Refresh อัปเดตข้อมูลอัตโนมัติ..."

"เมื่อแขก Walk-in เข้ามา พนักงานไม่ต้องกดเปลี่ยนหน้าจอไปมา สามารถคลิกที่การ์ดห้องพักเพื่อเปิด Center Split Modal กรอกข้อมูลแขก ระบบจะตรวจสอบความถูกต้อง และบันทึกเช็คอินเป็น Atomic Unit ทันทีครับ"

STEP 4

🖥️ การคลิกบนหน้าจอ:

  2. คลิกเลือกรายการห้อง 101 ที่กำลังพักอยู่ แล้วคลิก "เพิ่มค่าใช้จ่าย / มินิบาร์"
  3. เพิ่มน้ำดื่มหรือเครื่องดื่มมินิบาร์ 2 กระป๋อง ยอดเงินจะถูกคำนวณเข้า Folio ทันที
  4. เมื่อแขกคืนกุญแจ คลิก "เช็คเอาต์ & ปิดบิล"
  5. ระบบจะดึงยอดมัดจำกุญแจมาหักลบ และออกใบเสร็จรับเงินทางการให้ทันที
🗣️ สคริปต์คำพูดคุณเดียร์:

"ในจังหวะเช็คเอาต์ ระบบจะผสานงานแคชเชียร์เข้ามาในหน้าเดียว พนักงานสามารถดูค่ามินิบาร์และหักเงินมัดจำได้อัตโนมัติ..."

"และความพิเศษทางสถาปัตยกรรมของโปรเจกต์นี้คือ เมื่อกดยืนยัน Check-out ระบบจะส่ง Event กระจายงานแบบ 1:4 Fan-out ไปยังแม่บ้านให้อัตโนมัติ เพื่อสร้าง Task ทำความสะอาดด่วนทันที โดยพนักงานต้อนรับไม่ต้องโทรแจ้งแม่บ้านเลยครับ"

Anticipated Q&A Vault

เก็ง 5 คำถามยอดฮิตที่อาจารย์มักจะถาม พร้อมแนวทางการตอบแบบ SA มืออาชีพ

เตรียมคำตอบไว้ล่วงหน้าเพื่อให้ตอบได้อย่างมั่นใจ มีหลักการทั้งมิติธุรกิจและเทคนิค

Q1: "ทำไมถึงเลือกจำกัดขอบเขตแค่โรงแรมขนาดเล็ก 5–10 ห้อง? ไม่ดูเล็กเกินไปเหรอ?"

💡 แนวทางการตอบ:

"ที่เลือกขนาด 5–10 ห้อง เพราะนี่คือกลุ่ม Underserved Market ที่แท้จริงครับ โรงแรมใหญ่มีซอฟต์แวร์ระดับองค์กรดูแลอยู่แล้ว แต่โรงแรมขนาด 5–10 ห้องในไทยส่วนใหญ่ยังใช้สมุดจดเพราะไม่มีกำลังจ่ายค่าซอฟต์แวร์เดือนละหลายพันบาท การกำหนด Scope 5–10 ห้องทำให้เราสามารถออกแบบ UI แบบ Compact Single-screen ที่พนักงานคนเดียวดูแลได้ทั้งโรงแรม และยังพิสูจน์ได้ว่าสถาปัตยกรรม Serverless Edge ของเราสามารถรันระบบโรงแรมได้โดยมีต้นทุนค่าเซิร์ฟเวอร์แทบจะเป็นศูนย์บาทครับ"

Q2: "สถานะห้องพัก 7 สถานะ เยอะเกินไปไหมสำหรับโรงแรมขนาดเล็ก?"

💡 แนวทางการตอบ:

"ไม่เยอะเกินไปครับอาจารย์ เพราะทั้ง 7 สถานะสะท้อน ความรับผิดชอบของคนละฝ่ายอย่างชัดเจน ครับ: available/reserved/occupied เป็นหน้าที่ของฟรอนต์, checked_out/cleaning เป็นของแม่บ้าน, และ maintenance/out_of_order เป็นของช่างซ่อม การแยกสถานะให้ละเอียดทำให้ระบบสามารถตัดสินใจส่งงานแบบอัตโนมัติ (Automated Event Dispatching) ได้อย่างถูกต้อง ไม่เกิดข้อผิดพลาดในการเปิดขายห้องที่ชำรุดครับ"

Q3: "ถ้าตอนเช็คอินเกิดเน็ตหลุดหรือเครื่องค้าง ระบบจะเกิดข้อมูลผี หรือห้องสถานะพังไหม?"

💡 แนวทางการตอบ:

"ไม่พังแน่นอนครับ เพราะในระดับ Database ผมออกแบบให้ใช้ Cloudflare D1 Batch Atomic Unit ด้วยคำสั่ง await db.batch([...]) รวบคำสั่ง Update สถานะห้องพัก, บันทึกประวัติ และสร้าง Event ไว้ในธุรกรรมเดียว หากมีจังหวะใดสะดุด ระบบจะ Rollback คืนค่าทั้งหมดเสมือนไม่เคยมีอะไรเกิดขึ้น ข้อมูลจึงมีความสอดคล้อง (ACID Compliance) เสมอครับ"

Q4: "ระบบนี้ป้องกันการจองซ้ำ (Overbooking) ในระดับโค้ดอย่างไร?"

💡 แนวทางการตอบ:

"เราไม่ได้ตรวจแค่สถานะปัจจุบันของห้องครับ แต่เราใช้ Date Range Overlap Collision Query ในตารางการจอง โดยเช็คเงื่อนไขทางคณิตศาสตร์ว่า วันที่เข้าและออกที่ขอจองใหม่ ต้องไม่ทับซ้อนกับช่วงเวลาการจองเดิมที่ยังไม่ถูกยกเลิก (NOT (new_out <= check_in OR new_in >= check_out)) จึงป้องกันการจองซ้อนข้ามวันข้ามเดือนได้อย่างสมบูรณ์แบบครับ"

Q5: "ทำไมถึงต้องแยก Billing Service ออกจาก Reservation Service ทำไมไม่รวมไว้ด้วยกัน?"

💡 แนวทางการตอบ:

"ตามหลัก Single Responsibility Principle (SRP) ใน Microservices ครับ Reservation รับผิดชอบเรื่อง 'เวลาและการครอบครองห้อง' ส่วน Billing รับผิดชอบเรื่อง 'ธุรกรรมทางการเงินและภาษี' การแยกกันทำให้ระบบการเงินสามารถรองรับการเพิ่มค่าใช้จ่ายระหว่างพัก (มินิบาร์, รูมเซอร์วิส) ได้อย่างอิสระโดยไม่กระทบกับตารางการจอง และในอนาคตหากต้องการเชื่อมต่อระบบ Payment Gateway ภายนอก ก็สามารถทำที่ Billing Service ได้โดยไม่ต้องแก้ส่วนจองห้องพักเลยครับ"
